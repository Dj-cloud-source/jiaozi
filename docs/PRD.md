# 类 12306 高并发铁路票务系统 PRD v1

## 1. 项目定位

本项目是一个以铁路购票为业务场景的高并发票务系统。

项目目标不是完整复刻 12306，而是围绕一条完整的票务交易链路，承载后续的高并发、库存一致性、支付、Docker、Kubernetes、CI/CD、监控、压测和故障演练。

核心业务链路：

```text
查票
→ 选择车次
→ 填写乘车人
→ 确认下单
→ 自动分配座位
→ 锁定座位
→ 10 分钟内支付
→ 支付成功
→ 出票
→ 退票 / 行程完成
```

第一版优先保证核心购票闭环完整，不追求复杂铁路业务。

# 2. 用户角色

系统包含两类用户：

```text
普通用户
管理员
```

## 2.1 普通用户

普通用户支持：

* 手机号 + 密码注册
* 手机号 + 密码登录
* 查看和修改个人昵称
* 修改密码
* 查询车次
* 按车次号查询
* 按发车时间排序
* 按价格排序
* 查看实时余票
* 选择一等座 / 二等座
* 填写乘车人
* 提交订单
* 查看系统分配的座位号
* 支付
* 查看订单
* 查看电子票
* 取消待支付车票
* 退票
* 查看历史订单

用户登录状态统一有效 7 天。

第一版不支持：

* 手机验证码登录
* 找回密码短信
* 账号注销
* 头像
* 常用乘车人管理
* 用户封禁
* 验证码 / 反爬系统

# 3. 管理员

管理员账号由系统初始化时创建。

第一版只有一个管理员角色，不做复杂权限系统。

管理员支持：

* 管理站点
* 创建车次
* 修改未开售车次
* 配置票价
* 配置座位数量
* 配置开售时间
* 发布车次
* 查看用户
* 查看订单
* 按订单状态查询订单
* 按手机号查询订单
* 按车次号查询订单
* 处理异常订单
* 查看管理员操作日志

管理员所有写操作都需要记录审计日志。

第一版不做：

* 多管理员角色
* RBAC
* 用户封禁
* 系统监控看板
* 业务大屏

Prometheus、Grafana、Kubernetes 等属于运维系统，不属于管理员后台。

---

# 4. 站点

系统维护统一站点库。

例如：

```text
南京南
上海虹桥
杭州东
北京南
```

管理员创建车次时只能选择已有站点。

站点状态：

```text
ACTIVE
DISABLED
```

规则：

* 已使用过的站点不能物理删除
* 只能停用
* 停用站点不能用于新建车次
* 历史车次和历史订单仍然保留站点信息
* 出发站和目的站不能相同

---

# 5. 车次

一趟具体车次由：

```text
车次号 + 发车日期
```

唯一确定。

例如：

```text
G101 + 2026-09-20
G101 + 2026-09-21
```

属于两趟不同车次。

同一天不能创建两趟相同车次号。

车次号格式：

```text
1 个大写字母 + 1～4 位数字
```

例如：

```text
G101
D220
K88
T12
```

管理员创建车次时配置：

```text
车次号
发车日期
出发站
目的站
发车时间
到达时间
开售时间

一等座价格
二等座价格

一等座数量
二等座数量
```

第一版不支持跨天车次。

发车时间和到达时间必须属于同一天。

---

# 6. 车次生命周期

车次主要经历：

```text
草稿
↓
等待开售
↓
已开售
↓
已停售
↓
已发车
↓
历史车次
```

管理员首先完成所有车次配置。

配置完成后发布。

发布后等待指定开售时间。

到达开售时间后自动开售。

车次开售后：

```text
车次号
路线
日期
发车时间
到达时间
票价
座位数量
```

等核心信息不允许再修改。

发车前 10 分钟自动停止售票。

管理员不能手动提前停售。

发车后：

* 不再出现在正常查票结果中
* 历史订单仍然保留车次信息

---

# 7. 开售前展示

车次发布后但尚未开售时，普通用户可以提前看到车次。

展示：

```text
车次号
出发站
目的站
发车时间
到达时间
历时
票价
开售时间
开售倒计时
```

开售前：

```text
不能下单
不显示具体余票
```

到达开售时间后自动变成可购买状态。

---

# 8. 车票类型

第一版只支持：

```text
一等座
二等座
```

某种座位类型允许数量为 0。

例如：

```text
一等座：0
二等座：100
```

表示这趟车只出售二等座。

一等座和二等座是两个完全独立的座位池。

某一种座位类型售罄，不影响另一种继续销售。

---

# 9. 座位

座位使用纯数字编号。

例如：

```text
一等座：1～20
二等座：1～100
```

第一版不使用：

```text
5A
5B
5C
```

这类复杂座位号。

用户不能主动选择具体座位。

座位由系统自动分配。

分配规则：

```text
购买 1 张：
优先编号最小的可售座位

购买 2 张：
优先连续座位

如果存在多组连续座位：
优先编号更小的一组

如果没有连续座位：
允许分配两个不连续座位
```

例如：

```text
可售座位：
3、4、8、9、15

购买 2 张：
优先分配 3、4
```

---

# 10. 乘车人

购票账号和乘车人属于两个不同概念。

登录用户可以：

* 给自己买票
* 给其他人买票
* 同时给自己和其他人买票

乘车人信息包括：

```text
姓名
身份证号
```

普通用户页面中身份证号需要脱敏。

管理员可以查看完整身份证号。

同一身份证在同一趟车上只能存在一张有效车票。

第一版不判断不同车次之间是否存在时间冲突。

---

# 11. 购票数量

一次购票最多：

```text
2 张
```

一笔购票中的车票必须属于同一种座位类型。

允许：

```text
张三
李四

二等座 × 2
```

不允许：

```text
张三：一等座
李四：二等座
```

如果用户购买 2 张票，则两张票必须同时满足购票条件。

不做部分成交。

# 12. 购票确认

用户选择：

```text
车次
座位类型
乘车人
```

之后进入购票确认页。

确认页展示：

```text
车次号
出发站
目的站
发车日期
发车时间
座位类型
乘车人
单价
总价
```

只有用户点击：

```text
确认下单
```

之后才正式进入订单流程。

---

# 13. 下单

确认下单后，系统：

```text
自动分配座位
↓
锁定座位
↓
创建车票订单
↓
进入待支付状态
↓
开始 10 分钟支付倒计时
```

用户在支付前即可看到已经分配的座位号。

例如：

```text
张三 → 二等座 21 号
李四 → 二等座 22 号
```

每张车票拥有独立：

```text
订单号
乘车人
座位号
电子票
退票能力
```

即使两张票一次付款，也仍然是两张独立车票订单。

---

# 14. 待支付

下单成功后：

```text
支付时限：10 分钟
```

10 分钟内用户可以完成支付。

如果用户主动取消：

```text
车票订单取消
座位释放
```

如果 10 分钟没有完成支付：

```text
车票订单自动取消
座位释放
```

如果一次买了 2 张票：

```text
张三 → 21号
李四 → 22号
```

支付前允许单独取消其中一张。

例如取消李四：

```text
李四订单取消
22号释放

张三订单继续待支付
```

剩余车票的支付截止时间不重新计算。

---

# 15. 待支付期间禁止修改

车票订单生成后不能直接修改：

* 乘车人
* 身份证号
* 车次
* 座位类型
* 座位号

如果需要修改：

```text
取消原票
→ 重新下单
```

支付处理中禁止取消或修改本次参与支付的车票。

---

# 16. 支付

第一版使用：

```text
Mock Payment
```

用于完成完整支付业务流程。

第二阶段接入：

```text
支付宝 Sandbox
```

进行真实沙箱接口联调。

一次支付可以支付：

```text
1 张
或
2 张
```

车票。

不支持部分支付。

例如两张票均处于待支付状态：

```text
张三 ¥99
李四 ¥99
```

必须一起支付 ¥198。

如果只想支付一张：

```text
先取消另一张
→ 再支付剩余车票
```

---

# 17. 支付结果

支付成功：

```text
车票订单 → 已出票
座位 → 正式售出
生成电子票
```

第一版不存在：

```text
出票中
```

这一业务状态。

因为下单时已经完成座位分配和座位锁定。

因此：

```text
座位已锁定
+
支付成功
=
出票成功
```

支付失败时：

```text
车票仍然待支付
座位继续锁定
```

只要支付截止时间还没到，用户可以再次支付。

---

# 18. 电子票

每一张车票生成独立电子票。

电子票展示：

```text
订单号
车次号
出发站
目的站
发车日期
发车时间
到达时间
乘车人姓名
身份证号（脱敏）
座位类型
座位号
票价
出票时间
```

一次购买两张票时：

```text
张三 → 电子票 A
李四 → 电子票 B
```

不会合并成一张电子票。

后续增强功能：

```text
电子票二维码
扫码打开电子票详情页
```

第一版暂不实现。

---

# 19. 退票

发车前 10 分钟停止退票。

已出票车票允许单独退票。

例如：

```text
张三 → 21号
李四 → 22号
```

即使两张票一起支付，也可以只退其中一张。

用户确认退票后：

```text
车票立即失效
座位立即释放
```

退票确认后不可撤销。

释放后的座位重新进入可售状态。

如果车次之前已经售罄：

```text
有人退票
↓
座位重新可售
↓
车次重新出现余票
```

只要仍处于售票时间窗口，就可以再次出售。

---

# 20. 退款

退票和退款是两个不同业务。

用户确认退票后：

```text
车票业务立即完成
```

包括：

```text
电子票失效
座位释放
允许该乘车人重新购买同一趟车
```

随后系统处理资金退款。

退款是否已经真正到账，不影响：

* 原车票是否有效
* 座位是否重新出售
* 用户是否可以重新购票

第一版：

```text
全额退款
不收退票手续费
```

---

# 21. 行程完成

支付成功后车票进入：

```text
已出票
```

发车后但尚未到达目的地时，车票仍保持有效行程状态。

到达时间到达后：

```text
车票 → 已完成
```

历史订单继续保留。

---

# 22. 订单列表

用户只有一个订单列表。

不做：

* 待支付单独页面
* 已出票单独页面
* 已退款单独页面
* 状态筛选
* 日期筛选
* 单独乘车记录页

全部订单：

```text
按创建时间倒序展示
```

用户进入订单详情查看具体状态和电子票。

# 23. 查询车次

普通用户支持两种查询方式。

方式一：

```text
出发站
目的站
出发日期
```

方式二：

```text
车次号
```

查询结果支持：

```text
发车时间排序
价格排序
```

支持：

```text
升序
降序
```

第一版使用普通分页：

```text
每页 10 条
```

后续有时间可以增加游标分页。

---

# 24. 余票展示

车次尚未开售：

```text
不显示具体余票
```

车次开售后：

```text
显示一等座实时余票
显示二等座实时余票
```

某类座位售罄：

```text
一等座：售罄
二等座：剩余 32
```

车次所有座位全部售罄：

```text
车次仍然显示
状态：已售罄
```

如果之后产生退票：

```text
重新出现余票
```

---

# 25. 售票时间

车次到达指定开售时间后开始售票。

发车前：

```text
10 分钟
```

自动停止售票。

停售后：

* 车次仍然显示
* 不能下单
* 标记为已停售

发车后：

* 从正常查票结果中移除
* 历史订单继续保留

# 27. v1 核心闭环

第一版完成标准：

```text
管理员创建站点
↓
管理员创建车次
↓
配置票价 / 座位 / 开售时间
↓
发布车次
↓
定时开售
↓
用户查询车次
↓
选择座位类型
↓
填写乘车人
↓
确认下单
↓
系统自动分配并锁定座位
↓
生成独立车票订单
↓
10 分钟内支付
↓
支付成功
↓
出票
↓
生成电子票
↓
退票 / 到达完成
```

只要这条链路完整、稳定、可测试，v1 产品业务即视为完成。
